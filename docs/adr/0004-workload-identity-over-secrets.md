# 4. Workload Identity where the service supports it, connection strings where it does not

Date: 2026-09-21

## Status

Accepted

## Context

Every credential in a Kubernetes secret is a credential that has to be rotated,
scoped and kept out of logs. Azure AD workload identity removes the credential
entirely: the pod exchanges its projected service account token for an Azure AD
token, and access is expressed as a role assignment instead of a string.

Not every part of the stack can use it. PostgreSQL and Redis in this project
authenticate with a password and an access key, so those still travel as secrets.

## Decision

Each workload gets its own user-assigned identity, federated to its Kubernetes
service account:

| Identity | Access |
|----------|--------|
| `api` | Service Bus Data Sender, Key Vault Secrets User, Storage Blob Data **Reader** |
| `worker` | Service Bus Data Receiver, Key Vault Secrets User, Storage Blob Data **Contributor** |
| `keda` | Service Bus Data Receiver, for queue-depth scaling |

Blob access uses `DefaultAzureCredential`, which picks up the federated token in
the cluster and the developer's `az login` locally, so the same code runs in both
places. The report storage account has shared key authentication disabled
outright, so there is no key to leak even by accident.

What remains a secret: the PostgreSQL DSN, the Redis connection string, the
Service Bus connection string used by the SDK client, and the Application
Insights connection string. All four are generated by Terraform, stored in Key
Vault, and copied into a Kubernetes secret at deploy time — never committed.

## Consequences

The blast radius of a compromised API pod is limited to reading snapshots, not
overwriting them. Nothing has to rotate the blob credentials, because there are
none.

The trade-off is a slower first request while the token is fetched, and a class
of failure that only appears in the cluster: a federated credential whose subject
does not match the service account name fails at runtime, not at apply time.
